## WiFi 修复

原失败发生在固件读取阶段：芯片已被识别，但驱动无法打开
`/lib/firmware/aic8800d80/fw_patch_table_8800d80_u02.bin`。
厂商固件包实际安装目录是 `/lib/firmware/sdio/aic8800d80`。
板上 13 个文件已与冻结 Buildroot 目标逐项核对 SHA256；建立相对链接
`aic8800d80 -> sdio/aic8800d80` 后，加载成功并出现 wlan0。

这项修正属于系统层。原有 GitHub Draft 镜像和标签保持原样，不能把板上的修正
称为原镜像已包含。新的 post-build 及审计检查 13 个固件文件、相对链接和父目录；
不覆盖异常目录或链接，不复制其他芯片/总线的固件冒充 D80。
新增回归覆盖 U02 文件缺失、空文件、文件/目录/父目录链接和冲突别名，
这些错误均在替换其他启动策略前拒绝。

现场私有配置已通过静默参数输入配置给 WPA 控制接口，未传输配置文件载荷，
未输出密码或派生密钥。WPA 关联、DHCP、默认路由和局域网互通通过。
LYNX 转发使接收端看到的来源为已绑定 LYNX 主机地址，不能把 SDK 本机地址
直接当作传输对端。测试资料通过网络传送并校验哈希；用户配置、应用及数据的
私有备份通过双向 TLS 取回开发主机，33 个文件和两个 SQLite 数据库一致性检查通过。
网络/TLS 测试使用显式开发主机 UTC 校时，不视为 RTC/NTP 生产验收。

`S72dshancontrol-wifi` 在 S69 完成存储初始化后运行，使用系统固定 wlan0，
加载一次驱动、准备接口；没有站点配置时不发起关联。
站点配置放在 `/mnt/UDISK/dshancontrol/system/wifi.conf`，目录 root:0700，
文件 root:0600 或 root:0400，拒绝符号链接。配置不进入应用包或系统镜像。
启动器核对自有 supplicant 的可执行文件、PID 与完整参数；不停止外来进程，
不以重启进程掩盖失败。关联等待有界，DHCP 错误保留原退出码，日志只存于私有运行目录。
新 BusyBox 配方显式要求 stat 格式化、modprobe、IP address/link 和 udhcpc；
旧镜像缺少 stat，不能直接部署新启动器就宣称它已通过板上启动验收。

主机回归在 PID 修正后为 170 项通过（core 5 + 其余 165），其中新增 WiFi 启动器实际执行测试
验证缺配置、驱动/存储失败、私有文件权限、真实 PID 所有权和 DHCP 原码保留。
它们不能代替真实接入点、DHCP 服务器或重启联网测试。

第一次正常重启保留了真实启动失败：`wpa_supplicant -B` 返回时 PID 文件尚未就绪，
过早的所有权检查导致 S72 退出，关联随后完成但没有执行 DHCP。原生/应用健康正常。
已补充最多 5 秒的只读 PID/可执行文件/参数等待，不重复启动进程；
新增真实后台子进程延迟发布 PID、以及未发布 PID 时不重启两项回归。
修正后的主机检查通过，板端重启复测另行记录，不能把补执行 DHCP 视为自动启动通过。

## 更新器验证边界

复用现有 C++ CLI 回归矩阵，在板上执行已安装的原生二进制。
开发夹具使用单独的契约、测试公钥、合成载荷和生命周期钩子；
测试私钥仅在私有临时目录生成，不进入源码、镜像、发布附件或生产信任根。
试验目录固定在持久 ext4 卷，前后核对真实系统契约、出厂/当前应用身份和软件健康。
不停止/切换真实桌面，不改系统契约，也不把夹具的 test-rev/test-runtime 写成真实板卡身份。

该矩阵已在新板的实际已安装 C++ 二进制上完成 15 项测试、45 次 CLI 调用，
无失败、错误或跳过。真实系统配置、工厂/当前应用身份前后哈希一致，健康检查通过。
结果通过双向 TLS 取回并复核归档 SHA256，原始测试材料保存在本地忽略目录。
这验证真实 ARM 程序的算法、文件系统事务和进程故障恢复；
合成载荷与进程 SIGKILL 无法证明真实 Qt 应用升级、GUI 安装或电气掉电。
正式系统缺少生产公钥和准确硬件修订时继续拒绝安装，不放宽匹配。
后续真实应用/掉电试验前，先通过网络备份用户数据并验证恢复材料。

原始硬件日志、现场凭据与未脱敏备份仅保存在忽略的本地 `dist/`。
本任务不公开发布，不上传预览，未来板型仍各自等待独立构建和实板验收。

## 无 RTC 时的开机校时

第一次网络启动复测还发现正常重启后系统时钟回到 1970 年，会使 HTTPS 证书校验失败。
系统层新增 S73：在 S72 之后执行 `timeout 30 ntpd -n -q -p time.cloudflare.com`，
不启动常驻服务，不循环重试，保留工具的原始失败码；完成后拒绝仍早于 2026 年的时钟。
BusyBox 配方显式启用 timeout、NTP 客户端，禁用 NTP 服务器与隐式配置文件读取。
服务器使用 [Cloudflare 官方公布的 NTP 地址](https://developers.cloudflare.com/time-services/ntp/usage/)。
该方式是普通 NTP；没有 NTS 身份认证，也不构成工业安全时钟/RTC 保持资格。
上板网络校时、HTTPS 默认验证和重启自动恢复证据在后续验收记录中分别保存。
