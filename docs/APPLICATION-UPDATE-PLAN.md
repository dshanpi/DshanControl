## 1. 用户目标与参考范围

DshanControl 是独立的工业控制桌面应用系统。先稳定现有 T153 和本次
T113s4 SD NAND + Buildroot 接口，再独立开发、发布桌面及应用服务。
之后接入 A133、T527、RK3576、IMX6ULL-PRO、STM32MP157、RK3506，各板维护自己的系统适配，复用应用接口和更新协议。
这些未来目标尚未验收，不能从 CPU 名称推导兼容性，也不能共用一个未经验证的二进制。

参考 EinkOS 的发布标准，不复制其板卡配置、镜像哈希、版本标签或验收结论：

- [DSP-LINUX-001 1.1.0](https://github.com/dshanpi/EinkOS/blob/main/standards/linux-board-release/v1.1.0/SPEC.md)
- [历史系统版本关联](https://github.com/dshanpi/EinkOS/blob/main/docs/VERSIONS.md)

现行参考明确将历史的“每次发布都配镜像”限定在 system 线。
application 线只关联已验证的系统契约，不要求硬件仓库产生新提交。
本项目底层来源仍是 `DongshanPI/100ASK_T113s4-SdNand_TinaSDK5`，
不是参考中的 SPI NAND/OpenWrt 工程。SmartDesktopMimi 是另一项目。

## 3. 要真正分开的四层

| 层 | 归属 | 内容与边界 |
| --- | --- | --- |
| 桌面与业务 | 应用发布 | Qt HMI、Web 页面、业务 API、设备模型、报警/历史/配方、字体资源 |
| 稳定平台服务 | 系统发布 | 逻辑通道解析、背光/网络/现场总线硬件操作、能力发现、权限和维护互锁；通过版本化本地 IPC/API 提供服务 |
| 更新管理 | 系统发布 | 可信公钥、设备身份、更新任务、安装/恢复、健康判定；生命周期独立于被更新的桌面 |
| 板级系统 | 各板 BSP/系统发布 | Bootloader、内核、DTS、驱动、分区、Buildroot 基础库、板级配置与系统镜像 |

关键现状：应用包包括 `components/web/hmi_api.py`，其中仍直接执行 `ip`、
`qmicli`、背光及现场总线相关操作。已有 platform/channels 映射，但配置映射
不等于平台服务已与应用版本彻底分离。

建议先把这些直接硬件操作抽到系统拥有的平台服务，应用只调用稳定接口。
业务协议和连接逻辑是否随应用发布，按是否依赖板级权限/设备 ABI 划分，不能仅按
“用户态程序”归类。平台服务独立启动；应用使用最小权限，受控操作由服务校验。
只限制压缩包解压路径并不能阻止 root 应用运行后写系统，权限边界也必须实现。

整理目录时：保留 `components/hmi`、`web`、`core`；把通用应用载荷组装从
`scripts/install_s4_runtime.py` 抽成独立模块，避免通用发布工具导入 S4 安装器。
新增平台服务、接口测试和逐板适配入口；`boards/` 保留集成配方、来源及测试说明，
SDK 缓存和厂商二进制不入应用仓库。适配补丁最终由相应 BSP 发布锁固定。

## 4. 版本配对：来源锁定与兼容条件分开

| 记录 | 用途 | 更新规则 |
| --- | --- | --- |
| 系统发布锁 | 固定系统提交、硬件 H、SDK 全部输入/补丁、工具链、配置、出厂应用 A0、镜像和契约哈希 | 构建后生成；系统发布后不可变 |
| 系统契约 | 设备本机身份、接口版本、运行库/ABI、能力、更新器版本、受管目录 | 归系统管理；应用不能覆盖 |
| 应用发布清单 | 应用 A1、版本/序号、来源、每目标包及构建/验收材料、适用契约、升级路径 | 随应用发布并签名；不强制新增 H/SDK 构建 |
| 当前应用记录 | 当前 A1、包哈希、数据格式、已接受序号、失败版本及事务状态 | 由系统更新器维护；不得改写 A0 |

同一系统可从应用 A0 升至 A1、A2，而系统锁中的 A0/H/SDK/镜像哈希保持原值。
应用测试记录引用实际系统锁和镜像/契约哈希，既能追溯，又不绑定硬件分支最新状态。
镜像内契约不包含自身镜像哈希；外部系统锁关联二者，避免自引用。

首阶段保留当前精确匹配，禁止删除 board_id/runtime_id 检查来冒充通用。
未来如需一包覆盖多个经验证系统，用明确列举的兼容目标和逐目标证据扩展清单；
每个目标关联独立 build-info、目标包、sysroot/依赖来源和验收文件。
协议结构变化必须版本化，旧更新器拒绝不支持的新协议，由系统线升级更新器。
ABI 兼容家族与精确构建哈希应分别表达，不能直接拿“接口版本相同”替代验证。

## 5. GitHub 两条发布线

- `app-vX.Y.Z`：仅应用源码、逐目标 `.tar.gz`、`application-release.json`、签名、
  构建/验收记录、SHA256SUMS、版本说明。纯应用 Release 不附新系统镜像。
- `system-vX.Y.Z--BOARD`：逐板系统镜像、系统锁、契约、SDK/补丁/源码及实板记录。
  S4 保持厂商 IMAGEWTY 打包；是否压成 `.img.gz` 应核实 LYNX 消费方式，不能仅改后缀。

复用现有签名、安装与恢复代码；扩展发布工具支持一个应用版本汇总多个目标包。
构建流程拟为：固定干净提交 → 主机测试 → 固定各目标 sysroot 编译 → 制作草稿包 →
实板升级/回退验收 → 绑定验收文件并签名最终清单 → 上传草稿 → 下载远端附件复核 → 晋级。
CI 无板时只能完成编译和主机证据，不得生成实板 passed。私钥使用受控签名环境，
设备只预置公钥；首次基线、公钥轮换和更新器自身更新均走系统线。
这里描述的是后续发布流程，不是本轮上传或公开 Release 的动作。

设备流程：后台检查 → 显示兼容版本和失败原因 → 下载并校验 → 等待允许维护的状态 →
系统更新任务接管 → 停止相关应用 → 切换 → 启动/健康观察 → 成功确认或失败恢复。
安装任务不能归属于即将被停止的 HMI 子进程。安装期间平台服务保持对硬件状态的控制；
维护互锁需要覆盖整个切换窗口，不能只在停止前检查一次后放任新控制请求进入。

默认自动检查并提示；自动安装仅在设备策略显式启用且满足现场维护条件时运行。
稳定渠道不等于允许随时停机。数据继续独立于版本目录；v1 仅允许相同 schema，
数据迁移需另行实现备份、兼容读取、故障恢复和代码/数据一致回退后才开放。

| G08 恢复回退 | 暂存、停服务、切换、健康确认前后的真实掉电均可恢复；失败版本隔离 |
| G09 健康和数据 | HMI 功能心跳、平台 IPC/能力、Web 身份、数据库及业务数据通过，不能只查 PID |
| G10 跨板兼容 | 每个声明目标独立构建/验收，现有 T153 回归；未来板未测不列支持 |
