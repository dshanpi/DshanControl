# 区分应用更新、系统更新与烧录

**目标：** 选择正确的更新方式，并理解界面为何可能拒绝安装。当前公开应用基线为源码预览，历史试验不能直接当作生产 OTA 就绪证明。

## 三条交付路径

| 类型 | 内容 | 用户数据与系统关系 |
| --- | --- | --- |
| source preview | 已提交源码与校验值 | 在开发主机使用，不安装到更新器 |
| application | HMI、Web、业务服务和应用资源 | 更新应用版本目录，保留系统和独立用户数据 |
| system | BSP、内核、DTB、基础库、系统契约与预装应用 | 按系统专用流程安装；工厂镜像可能清空数据 |

源码标签通常为 `source-*`，应用标签为 `app-vX.Y.Z`，系统标签为 `system-vX.Y.Z--BOARD`。标签名称只是分类，仍需检查清单和附件。

## 应用更新前核对

设备必须具备可核验的板型、硬件修订、架构/float ABI/libc、runtime ID、系统契约、更新器协议、渠道、公钥及真实维护检查。签名证明来源，不能证明兼容或功能质量。

默认拒绝 pending 契约或身份不匹配是正常保护，不要用开发标志、空回调或实验室脚本绕过现场门禁。

## 用户操作流程

1. 先备份配置与业务数据，确认当前设备允许维护。
2. 打开“应用更新”，记录当前版本和兼容性信息。
3. 点击“检查更新”，核对目标版本、渠道和摘要。
4. 使用“查看兼容性详情”确认目标身份匹配。
5. 点击“下载更新”，等待下载及完整性检查结果。
6. 只有全部前置检查通过，再确认安装。
7. 根据当前任务 ID 查看阶段和结果，完成后核对实际应用身份及数据。

检查、下载和安装是不同动作。下载成功不意味着安装完成；界面变新也不证明重启后仍运行新版本。

## 安装事务怎样工作

系统运行端负责安装锁、空间检查、受限载荷、持久日志、原子切换、健康观察和失败回退。v1 要求数据格式一致，不允许包中携带迁移/安装脚本。应用包不能覆盖系统库或内核。

异常时保留初始失败、恢复阶段和原始错误码。断电恢复是继续已有事务，不等于盲目重发安装任务。回退失败时需要保留事务供恢复流程处理。

## 系统镜像烧录

仅在拿到对应板卡的完整交付资料时进行：核对型号/存储 → 校验 SHA256 → 确认清空范围和备份 → 用对应工具检查镜像 → 按板级步骤烧录 → 检查首次启动、应用、数据和恢复路径。

本教程没有给未公开候选生成下载入口。包含 `CLEARS-DATA` 或空工厂 UDISK 的镜像不能解释为保数据升级。操作完成提示只能证明工具的该阶段结果，仍需验证实板启动和物理功能。

## 常见拒绝

| 提示类别 | 应如何处理 |
| --- | --- |
| 身份/契约不匹配 | 获取匹配该系统的目标包，不编辑身份绕过 |
| 签名失败 | 检查来源、完整性和系统已信任公钥 |
| 维护状态不满足 | 等设备进入真实可维护状态 |
| 空间或数据卷异常 | 保留数据，按恢复流程处理，不在启动时格式化 |
| 健康检查失败 | 核对日志、运行身份和回退结果 |
