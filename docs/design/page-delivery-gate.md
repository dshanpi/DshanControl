# 逐页设计与交付门禁

从本轮开始，界面工作按“设计图 → 用户查看与反馈 → 单页修正与评审 → 实现 → 主机验证 → 系统打包与实机验证”推进。依据用户 2026-10-29 的要求，先给用户看渲染图，再实现页面；不能因已授权烧写而跳过页面设计评审。

## 页面与记录
`page-gates/manifest.json` 列出 24 个不同的应用页面/子页。不同入口路由不重复计页；工作台、全部应用、确认框、文件选择、详情和更新结果等公共界面另外列入影响范围，不能由主页面截图代替验收。

每页独立 JSON，必须持续记录：
- 业务目标、开始条件、完整业务流程、主操作和操作步骤。
- 服务或设备如何确认结果；失败、离线、空数据、等待、取消如何恢复。
- 保留、增加、修改、删除的功能逐项列明；尚未接入的提案单列，不能显示成已可用。
- 设计图编号与完整 SHA、真实评审意见来源、尚未解决的偏差。
- 每次实现摘要、涉及源码 SHA、验证日志、真实界面截图及遗留风险。
- 实机验证单独记录；概念图、主机合成状态和构建成功不能作实机通过证据。

## 执行方式
1. 先从现有代码和服务契约填写记录，再渲染。首轮四张六页总览只用于风格和信息层级讨论，不是逐控件定稿。
2. 按用户反馈精修单页与必要弹窗；保留所有旧图及偏差。只有真实评审同意且图中问题已解决，才把 `design_review.decision` 改为 `approved`，引用消息或评审记录。不得代替用户虚填批准。
3. 开始实现前运行 `python3 scripts/check_ui_page_gates.py --phase design --pages Pxx`。没有评审记录或仍有图稿偏差时拒绝。
4. 实现过程中逐项更新功能变化和实际操作步骤。完成时将 `status` 置为 `implemented`，绑定源码、测试、截图。共享文件改动必须在 `manifest.impact_reviews` 中列出全部受影响页和理由；每一页都要包含相同的当前源码摘要。
5. `make check-ui-pages` 检查账本与源码绑定；它也是 `make test-hmi` 和 `make package` 的前置条件。新增、删除或修改 HMI 目录中的源码、图像、字体、资源与构建定义同样检查，删除摘要写为 `deleted`。
6. 只改门禁工具/文档时运行门禁单元测试，不重复未变化的界面或后端矩阵。真正改动 UI 后运行相关行为测试、完整 HMI 检查及仓库要求的检查，保存失败和修复记录。
7. 页级通过后才进入完整系统候选检查与烧写；原有能力、维护互锁、媒体和恢复检查继续有效。已有烧写授权不用重复索取。烧写后记录实际系统身份、界面与手指操作结果，不能由旧固件或旧观察代替。

## 自动检查的边界
检查器验证记录结构和文件摘要，不能鉴定评审消息、截图或测试日志的真实性，也不能自动推断一个共享源码文件影响了哪些页面；这些必须由代码评审核对。不得通过改动基线、缩小影响页集合或填入虚假证据绕过检查。基线是本轮之前的固定源码提交 4390dc6f254deebdc113410d85dfcdedb4ccfffa；后续更换基线需要另存完整历史账本和明确评审，不随实现自动推进。

当前全部页面为设计待评审，功能新增为空不表示批准新增功能，也不表示所有业务已完成。生成式渲染存在字段/按钮偏差时，必须在页面的 `known_gaps` 中记录并阻止实现。

## 每次实现都留历史
每次页面实现均在该页 implementation.history 追加一条独立记录，含日期/编号、业务与操作流程、功能增减、源码绑定、测试和截图引用。先前记录不得覆盖，通用记录随源码提交；原始证据留 SDK 交付目录。代码评审必须核对历史追加情况。当前尚未实现新设计，history 为空，不伪填本次 UI 交付。
